## 1. Product summary
Recall ingests meeting transcripts and does much more than summarize. It extracts summaries, topics, participants, decisions, and action items (assignee, deadline, status), stores them with the exact transcript evidence, and lets the user chat with one meeting or the entire meeting history. Every answer carries citations back to meetings and transcript lines. Its distinguishing feature is CROSS-MEETING CONTEXTUAL MEMORY: it connects information across meetings (e.g. "What happened with our database migration?" gives a chronological narrative across meetings; "What changed between meeting 1 and 3?" gives a comparison).
This is an academic NLP project. The NLP components must be separable, explicit and measurable, so faculty can identify each technique, and an evaluation harness is a first-class deliverable.

Target machine: MacBook M2 Air, 24 GB unified memory, macOS, no CUDA. Use CPU/MPS-friendly models. Everything runs locally; the only external service is a local Ollama server.

## 5. Backend: processing pipeline (`pipeline.py`), run as a FastAPI BackgroundTask; meeting.status transitions uploaded, processing, ready (or failed with error_message). Each stage wrapped in try/except with logging so one failing stage doesn't lose the others where possible.

### 5.1 Ingestion
- Accept .txt, .docx, .pdf (and .vtt/.srt as a bonus). Extract text. Reject files over 10 MB.
- `transcript_parser.py`: parse into utterances. Support these formats via regex, auto-detected:
  1. `Speaker: text`
  2. `[HH:MM:SS] Speaker: text` and `HH:MM:SS Speaker: text`
  3. `Speaker (HH:MM:SS): text`
  4. Unlabeled paragraphs → speaker "Unknown".
  Continuation lines without a speaker are appended to the previous utterance. Normalize speaker names (strip, title-case, merge case variants).
- Preprocess: unicode normalization, whitespace cleanup, optional filler removal (um, uh) ONLY for the text sent to summarizers, never in stored evidence text. Tokenization/sentence splitting via spaCy.
- Meeting date: from the upload form; else try to parse from filename/first lines; else today.

### 5.2 Chunking
Group consecutive utterances into chunks of about 200 tokens (min 80, max 300) with 1-utterance overlap; never split an utterance unless it exceeds the max. Store utterance_start_idx/end_idx. Chunk text format: `[Speaker]: text` lines.

### 5.3 Summarization (nlp/summarize.py)
Implement three methods behind one interface `summarize(meeting, method)`:
- `bart` and `t5`: MAP-REDUCE (the models have ~1024-token limits): chunk the cleaned transcript into ~700-token windows, summarize each, concatenate, then summarize the concatenation (recursively if still too long). Set sensible min/max lengths.
- `llm`: map-reduce with Ollama; final output is a structured summary: 3-6 sentence overview + key points.
Run `llm` as primary; run bart and t5 only when `RUN_BASELINE_SUMMARIZERS=true` (default true for eval, false in the UI path to keep uploads fast). Models are lazy-loaded singletons.

### 5.4 NER and topics
- spaCy NER over utterances: store PERSON, ORG, DATE, TIME, GPE, PRODUCT, EVENT, MONEY with utterance_idx. Add a spaCy EntityRuler with patterns for common tech terms (PostgreSQL, MongoDB, FastAPI, React, AWS, etc.).
- Participants come from speaker labels, plus PERSON entities mentioned but not speaking (store in entities).
- Topics: KeyBERT (keyphrase_ngram_range (1,3), top_n=8, MMR diversity 0.5) on the cleaned transcript, using the shared MiniLM model. Store top topics with scores.

### 5.5 Action item extraction (nlp/actions.py), the most important component
Two extractors behind one interface:
A) `rules` baseline: regex + spaCy dependency patterns for commitments and requests ("I'll", "I will", "I can take", "let me", "we need to", "we should", "can you", "please", "X will", "action item:", "by <date>", "before <date>", "next week"), assigning the speaker for first-person commitments and the addressee/named person otherwise.
B) `llm` (primary): process the transcript in overlapping windows (about 40 utterances, 8 overlap). Each utterance is prefixed with its idx, e.g. `[12] Rahul: ...`. Prompt the LLM (system prompt in rag/prompts.py or nlp/prompts) to return ONLY JSON:
```json
{"action_items":[{"task":"imperative phrase, e.g. Complete authentication module","assignee":"name or null","deadline_text":"as spoken or null","evidence_utterance_idx":12,"evidence_quote":"verbatim words from that utterance","assignee_explicit":true,"deadline_explicit":true,"confidence":0.0}]}
```
Prompt rules: only commitments/assignments actually stated; never invent assignees or deadlines (use null); "I'll X" means assignee = the speaker; mark explicit=false if assignee/deadline is inferred from context; include 2 few-shot examples (use the Rahul/Anshuman example: "We need to complete the authentication module by Friday." / "I'll handle the API integration." / "Great, I'll take care of testing.").
Post-processing (mandatory):
1. Validate evidence: `rapidfuzz.fuzz.partial_ratio(evidence_quote, utterance.text) >= 85` on the stated utterance idx (allow ±1 neighbor); else DROP the item.
2. Normalize assignee to a known participant via fuzzy match (>=85) else keep the raw name; first-person → the speaker.
3. Resolve deadline_text to deadline_date with `dateparser` (settings: RELATIVE_BASE=meeting_date, PREFER_DATES_FROM='future'); keep deadline_text regardless.
4. Deduplicate within the meeting (MiniLM cosine > 0.85 on task text) keeping the highest-confidence item.
5. Retry once on invalid JSON, then log and skip the window.
Default status = pending.

### 5.6 Decision detection (nlp/decisions.py)
- `rules` baseline: cue phrases ("we decided", "let's go with", "we'll use", "agreed", "the decision is", "we're going with", "approved", "final call").
- `llm` (primary): windowed JSON extraction like actions: `{"decisions":[{"decision":"...","topic":"short label","evidence_utterance_idx":n,"evidence_quote":"..."}]}` with the same evidence validation and dedup.
- Supersession (knowledge/supersession.py), behind config SUPERSESSION=true: for each new decision, find prior decisions from EARLIER meetings with embedding cosine > 0.6; ask the LLM `{"relationship":"supersedes|consistent|unrelated","reason":"..."}`; on "supersedes" set the old decision status=superseded and superseded_by_id=new.

### 5.7 Indexing (knowledge/)
- Embeddings: sentence-transformers all-MiniLM-L6-v2, normalized, batch encode.
- FAISS: one `IndexIDMap(IndexFlatIP(384))` persisted to `data/faiss.index`. Index three doc types: chunks, action items (text = "Action item: {task}. Assignee: {assignee}. Deadline: {deadline_text}. Meeting: {title} ({date})"), decisions ("Decision: {decision}. Topic: ..."). Record each in `vector_docs`. Deleting a meeting rebuilds the index from DB (simple and correct).
- BM25: rank_bm25 built in-memory from the same docs; rebuild at startup and after ingest changes.
- Hybrid (`hybrid.py`): Reciprocal Rank Fusion (k=60) of dense and BM25 rankings. Expose `retrieve(query, mode='dense|bm25|hybrid', top_k, meeting_ids=None, per_meeting_cap=None)`, used by both chat and eval.

## 6. Backend: Conversational RAG (rag/)
`POST /api/chat` flow:
1. Load the conversation's last 6 messages. Rewrite the follow-up question into a standalone query with the LLM (skip if there is no history).
2. Scope: `meeting_ids` filter from the request, otherwise all meetings.
3. Retrieve with hybrid mode, top 12 candidates. If scope is all meetings, enforce a per-meeting cap of 3 so evidence spans meetings, then keep the best 8-10 and SORT CHRONOLOGICALLY by meeting_date (then position).
4. Build the context as numbered sources: `[S1] Meeting "Title" (YYYY-MM-DD), lines 12-18: ...` (for action/decision docs, label type and include the structured fields and the evidence quote).
5. Detect structured intents (keywords: "pending", "tasks", "who is assigned", "deadline", "overdue", "decisions") and additionally inject the relevant SQL results (e.g. pending action items with assignee/deadline/meeting) as sources labeled `[DB]`.
6. Answer prompt rules: answer ONLY from the sources; cite with [S#] after each claim; when asked about change over time, narrate chronologically by meeting date; if the sources don't contain the answer, reply exactly with a clear "I couldn't find that in your meetings" style message and cite nothing; never invent names, dates, or numbers. Return JSON `{"answer":"...","used_sources":["S1","S3"]}`.
7. Citation verification (citations.py): drop any cited id that doesn't exist; map the remaining ones to `{meeting_id, meeting_title, meeting_date, utterance_start_idx, utterance_end_idx, snippet}`.
8. Persist the user and assistant messages (with citations JSONB) and return them.
Also implement `POST /api/meetings/compare` (body: meeting_ids[2+]): retrieves per-meeting summaries, decisions and action items and returns an LLM-written comparison (what's new, what changed, what was dropped) with citations.

## 9. Evaluation harness (`eval/`), mandatory; run with `make eval`, results written to `eval/results/` as CSV + a markdown report + PNG charts, and summarized in docs/EVALUATION.md
- Gold data: generate 5 synthetic but realistic meetings in `eval/data/meetings/` (software-team, 600-1500 words each, 3-5 speakers; meetings 1-3 follow the database migration story: Nov 10 discuss migrating to PostgreSQL; Nov 12 decide PostgreSQL over MongoDB; Nov 15 migration delays and schema changes; include a later decision that reverses an earlier one in meeting 4 or 5, plus some unassigned tasks and some deadlines like "by Friday"). Write hand-checked gold JSON in `eval/data/gold/<meeting>.json` (entities, action items, decisions, summary key points) and `eval/data/qa_gold.json` with at least 30 questions (single-meeting, cross-meeting, "what changed", pending-tasks, and 4 unanswerable ones) each with expected answer keywords, gold meeting ids and gold evidence utterance ranges.
- Summarization: ROUGE-1/2/L (rouge-score) for BART vs T5 vs LLM, on 100 samples of the DialogSum test split (HuggingFace `datasets`, skip gracefully if offline and say so) AND on the gold meetings' reference summaries.
- NER: spaCy precision/recall/F1 per label vs gold entities (span-level, case-insensitive), with and without the EntityRuler.
- Action extraction: P/R/F1 for rules vs LLM (a match = same assignee-normalized item with embedding similarity > 0.7 on the task) plus field accuracy for assignee and deadline separately.
- Decision detection: P/R/F1 rules vs LLM.
- Retrieval: Recall@1/3/5/10 and MRR comparing BM25 vs dense vs hybrid(RRF), using the gold evidence ranges.
- QA: answer correctness (keyword-coverage score plus optional LLM-as-judge, flagged clearly), citation accuracy (fraction of cited sources overlapping gold evidence), citation precision/recall, and correct-refusal rate on unanswerable questions.
- Everything is seeded and reproducible; each script is runnable on its own: `python -m eval.eval_retrieval`.
